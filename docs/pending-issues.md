## Rust N 维护及资格确认的剩余分析开销

归属：`MONOREPO-362`。责任模块：`wavequant-quant-rs`。当前记录为后续待处理事项，本次仅整理文档，没有执行新的优化或测量。

### 问题与当前结论

当前 v29 加入共享 N 维护和资格确认后，分析总耗时仍高于纯趋势计算。需要分别定位 N 的维护成本和资格规则的成本，不能把整套额外开销都归为“资格确认很慢”。

本次基线来自国芳集团 `sh.601086`，2018-01-02 至 2026-10-23，共 2135 根因果前复权日线。三组使用同一冻结二进制、同一行情字节；每组预热 3 次，独立进程轮换采样 9 次。

v30新增趋势悬停所需的N使用区间和目标变化快照；下列仍是已保存的v29基线。v30的记录开销、返回体积与分析缓存变化尚未重新测量，后续对照时应同时记录，不能直接沿用v29数字。

### 已有事实和仍未确定的部分

- 三组完整四级趋势结果（含段六态与可知时钟）一致；开启／关闭资格时，完整 `nMemory` 和 `nRecords` 数据一致。开启组二级返回 6 条资格记录，其中 1 条确认当日结束；未据此确认与旧 Python 区间等价。
- 当前关闭买点资格开关仍会维护 N，供后续 ABC 判断等消费者使用。不能为降低数字直接删除 N 阶段，或将资格关闭组当作纯趋势。
- N 维护是本次较大的额外阶段，但现有计时不能证明其中某个转换、扫描或集合操作是主要原因，需要进一步细分后再决定修改位置。
- 资格消费者仍包含 N／ABC、独立量价、缺口、普通回撤及资格结束判断。各通道独立占比和历史扫描净成本，本次没有测出。
- 本次仅测算法分析，不包含 SDK／Redis 取数、复权、Worker 通讯、HTTP、VO 投影、编码压缩、缓存读写及图表渲染。页面若仍显示秒级等待，需要另外沿真实请求链路定位，不能将 44.4290ms 当作页面总耗时。

### 后续处理方向

1. 先拆分共享 N 准备、候选读取／去重、当前索引绑定、防守与轧空推进、目标推进的耗时及调用次数，确认 9.4500ms 主要花在哪里。
2. 拆分资格消费者中的 N／ABC、量价、缺口、普通回撤和结束检查，确认是否仍有可改为游标或累计状态的历史扫描。
3. 区分一次性来源整理与逐日工作；只在数据或状态变化时更新可复用信息。是否改造以实际计时为依据，保留当日可知时钟。
4. 优化后用同输入、同工具链、同 profile、同参数重新采样，报告总耗时、各阶段、波动范围和结果差异。若修改规则，先明确行为变化，不能把结果变化当作纯性能优化。

### 处理时必须保持的边界

- 同一趋势只维护第一条当前有效 N；严格破位后寻找下一条，新趋势切换自己的 N。跨级共用索引，历史记录不订阅每日维护。
- ABC 判断读取当日已经确认且有效的 N；不能用最终共享 N 状态回填历史，也不能仅凭 N 轧空直接开启交易资格。
- 不改变折线和一至三级共用趋势算法、资格开关含义、确认及结束规则，不更改旧 Python 业务。
- 后续取得相应验证授权时，对照完整四级结构、N 表及引用、资格区间与确定性；数据量或缓存变化另行测量，不从时间数字推算。

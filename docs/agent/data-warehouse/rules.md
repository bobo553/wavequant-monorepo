# 数据数仓规范

本文件仅在任务涉及 ETL/ELT、CDC、指标、事实/维度模型、分析数据集、数据质量或血缘时加载。业务 PostgreSQL、Redis 和搜索实现仍读取 `docs/agent/backend/data-rules.md`。

## 读取路由

| 任务类型                                 | 额外读取文件                                              |
| ---------------------------------------- | --------------------------------------------------------- |
| 数仓边界、基础建模、增量处理和质量门禁   | 本文件                                                    |
| 埋点、事件契约、采集 SDK、会话或曝光日志 | `docs/agent/data-warehouse/tracking-rules.md`             |

在线事务数据库仍按后端数据规则实现；只有分析链路才加载本领域专项文件。

## 范围与所有权

- OLTP 服务数据库是业务事实来源，数仓负责分析和决策，不反向承载登录、支付、权益等在线事务。
- 每个数据集明确 Owner、消费者、粒度、主键、更新频率、保留期、敏感级别和 SLA；没有消费者的数据不提前建设。
- 原始层保留可重放输入，清洗/标准层统一语义，主题/数据集市面向消费；禁止业务报表直接依赖未治理原始表。
- 生产服务不得直接查询数仓完成核心请求，数仓延迟或重建不能影响在线交易正确性。

## 模型与指标

- 事实表先定义一行代表的业务粒度，再定义维度和度量；不同粒度不得混入同一事实表。
- 指标必须有唯一名称、业务定义、公式、时间口径、过滤范围、维度、单位和负责人，避免多套 SQL 各自解释。
- 金额保留币种和定点精度；比率保存分子分母或可重算明细，不只保存已舍入结果。
- 维度变更明确采用覆盖、保留历史或其他 SCD 策略；代理键与业务键职责分离。
- 区分事件时间、处理时间和业务日期；时区转换只在展示或明确口径层完成。

## 采集与增量处理

- 优先使用可重放日志、CDC 或版本化事件采集；从业务表抽取时限制负载并避免长事务和无界全表扫描。
- Pipeline 必须幂等、可重跑、可回填和可从检查点恢复；同一批次重复执行不能重复累计指标。
- 增量任务使用稳定 Watermark/游标，定义迟到、乱序、重复和删除数据的处理策略。
- Schema 演进先兼容消费者；字段重命名、类型变化和删除需要迁移窗口与影响清单。
- 回填与日常增量使用同一转换逻辑，避免两套实现产生历史/实时口径差异。

## 数据质量与血缘

- 在入口和关键转换后检查唯一性、完整性、引用一致性、范围、分布漂移、行数和新鲜度。
- 质量失败按严重性阻断发布、隔离分区或告警；禁止用零值静默填充未知错误。
- 数据血缘至少覆盖来源、转换、目标、调度任务和下游看板；破坏性变更前能定位所有消费者。
- 每批记录批次 ID、代码/Schema 版本、输入范围、输出行数、质量结果和重试状态，便于审计与重放。

## 隐私、权限与成本

- 按最小必要原则采集个人信息；开发、测试和分析使用脱敏/匿名数据，禁止复制生产敏感明文。
- 权限按数据域、敏感级别和用途授予；导出、下载和跨域共享需要审计与到期控制。
- 分区、聚簇和文件大小依据查询模式设计；避免大量小文件、无谓全量刷新和高基数无边界聚合。
- 建立扫描量、存储、任务耗时、失败和闲置数据集指标；成本优化不能破坏正确性和可重放能力。

## 验证要求

- 转换逻辑使用固定样本与边界数据单测，关键指标执行源数据对账和独立重算。
- 验证空批次、重复批次、迟到数据、Schema 变化、任务中断、回填和下游兼容。
- 发布前运行数据契约、质量、血缘和权限检查，并记录数据时间范围与结果证据。

# 可观测性与事故响应专项规范

本文件用于 SLI/SLO、日志、指标、Trace、告警、Runbook、事故响应和复盘。服务内错误处理和重试仍读取后端可靠性规则。

## SLI、SLO 与错误预算

- SLI 从真实用户旅程定义成功、延迟、新鲜度或正确性，明确测量点、总体、排除和统计窗口。
- SLO 根据用户期望、业务风险和实际基线设定；SLA 是外部承诺，阈值应留出内部处置空间。
- 使用分位数或分桶观察尾延迟，不以平均值掩盖慢请求；低流量服务同时展示样本量和长窗口。
- 错误预算用于平衡可靠性和发布速度；预算快速消耗时限制高风险发布并优先消除主要故障来源。

## 信号与关联

- 指标覆盖流量、错误、延迟和饱和，并补充业务正确性、队列积压、数据新鲜度和依赖健康。
- 日志结构化且事件名稳定，包含服务、环境、版本、时间、请求/Trace 标识和必要业务上下文；不得包含秘密或完整敏感数据。
- Trace 跨 HTTP、消息和后台任务传播 trace、correlation、causation 标识，标明采样和丢失；不能把高基数业务 ID 放进指标 Label。
- 观测数据有保留期、访问控制和成本预算；采样不能丢失全部错误、慢请求或安全事件。
- Dashboard 围绕用户影响、服务依赖和处置动作组织，并展示版本/发布标记与数据新鲜度。

## 告警与 Runbook

- 告警优先基于 SLO 消耗、持续用户影响和容量趋势，设置去重、抑制、维护窗口和恢复通知。
- 每个告警有 Owner、严重性、影响说明、Dashboard、Runbook、升级路径和可执行动作；无行动价值的告警删除或降级。
- 严重性依据用户、业务、数据和安全影响评定，不用固定分钟数冒充所有系统通用标准。
- Runbook 包含确认、止损、回滚/降级、证据保全、沟通和恢复验证；命令标明环境、权限和副作用。

## 事故响应

- 重大事故明确 Incident Commander、技术负责人和沟通负责人；同一人可兼任，但决策与信息出口必须清晰。
- 先控制影响、恢复核心能力和保护数据，再深入定位根因；恢复过程中不得绕过鉴权、账本或审计底线。
- 时间线记录检测、确认、关键决策、操作、指标变化和恢复，并区分事件时间与记录时间。
- 对内外沟通只陈述已确认事实、影响、缓解和下一更新时间，不猜测根因或泄露敏感细节。
- 恢复后验证用户链路、数据一致性、积压、补偿、告警和容量，不能以“进程恢复”直接宣布结束。

## 复盘与改进

- 复盘聚焦系统条件、决策环境和防护缺口，不归咎个人；分析触发原因、放大因素、检测与恢复为何有效或失效。
- 行动项必须具体、可验证、有 Owner、优先级和期限，覆盖预防、检测、缓解和恢复，而非只写“加强注意”。
- 对相似服务检查同类风险，更新测试、告警、Runbook、容量和架构决策，并追踪行动关闭证据。
- 事故资料按敏感等级控制访问和保留；可公开经验需要脱敏并避免暴露攻击面。

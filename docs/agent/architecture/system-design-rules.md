# 系统设计专项规范

本文件用于新系统、重大能力、容量设计、技术选型和 ADR。目标是把假设、约束和验证方式变成可检查的设计输入，而不是输出固定模板。

## 需求与约束

- 先明确参与者、核心用例、数据边界、成功条件和明确不做的范围，再讨论组件和技术栈。
- 非功能需求至少评估延迟、吞吐、可用性、一致性、恢复、隐私、安全、合规、成本和交付周期，并标明优先级。
- 区分硬约束、当前事实、估算假设和偏好；未知量列为待验证项，不能用精确数字伪装确定性。
- 识别读写比例、峰谷、突发、数据增长、保留期、地域、终端和外部依赖限制；平均值不能替代峰值与尾延迟。

## 容量与数据流

- 容量估算写出公式、单位、时间窗口、数据来源和安全余量，使用范围而不是单点预测。
- 沿入口、计算、存储、队列、缓存和出口画出关键数据流，标明同步/异步、所有者、信任边界和背压位置。
- 分别评估正常峰值、依赖变慢、积压恢复、回填/迁移和区域故障；设计需要说明最先饱和的位置及可观察信号。
- 缓存、分片、读写分离、队列和多地域只能由已识别瓶颈或目标驱动，并包含一致性、失效、恢复和成本代价。

## 方案与决策

- 每个候选方案比较功能适配、复杂度、团队能力、生态维护、安全、锁定风险、运行成本和迁移可逆性。
- 关键技术用最小 PoC、真实数据 Benchmark 或故障实验验证；单次跑分、厂商宣传或流行度不作为决策依据。
- ADR 至少包含背景、决策、候选方案、取舍、影响、迁移、回滚、验证和待复审条件。
- 优先选择满足当前目标且可演进的最小方案；不得按用户量、表行数或团队人数套用固定架构等级。

## 交付与复审

- 设计必须落到契约、数据所有权、部署单元、权限、观测、容量告警、降级和恢复责任人。
- 高风险假设在上线前进入验证清单；无法验证的内容记录风险、监控和触发复审的阈值。
- 架构评审检查失败模式、回滚路径和运维负担，不只检查正常请求流程。
- 实际流量、成本或故障模式显著偏离假设时复审决策；不要为维护文档外观而保留失真的设计。

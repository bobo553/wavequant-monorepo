# 架构规范

本文件仅在任务涉及应用/服务拆分、模块边界、依赖方向、跨系统协作、技术选型或重大演进时加载。普通功能实现不需要读取本文件。

## 读取路由

| 任务类型                                         | 额外读取文件                                           |
| ------------------------------------------------ | ------------------------------------------------------ |
| 应用/服务边界、依赖方向和一般架构演进            | 本文件                                                 |
| NestJS 服务内分层、模块和进程边界                | `docs/agent/backend/architecture-rules.md`             |
| 需求澄清、容量估算、技术选型、ADR 或成本权衡     | `docs/agent/architecture/system-design-rules.md`       |
| 分布式一致性、跨服务事务、时钟、容错或高可用设计 | `docs/agent/architecture/distributed-systems-rules.md` |

跨领域设计再按需加载后端、数据数仓、运维或安全规则。后端实现先由后端架构专项落地，再按本文件选择通用架构细则；不因“架构任务”读取全部目录。

## 事实与决策

- 先读取根 README、目标应用 README、相邻代码和运行配置，以代码事实而不是目录名猜测架构。
- 重大决策记录目标、约束、候选方案、取舍、迁移、回滚和验证方式；无法逆转或影响多个团队时使用 ADR 或等效文档。
- 选择技术栈时综合业务、团队能力、开发周期、运行成本、生态、安全和维护年限，不以单次基准、流行度或语言偏好决定。
- 架构图和文档必须对应当前实现；变更边界时同步契约、部署、数据所有权、观测和文档。

## 边界与拆分

- 默认从模块化单体或少量明确服务开始；不能按代码行数、用户量、数据规模或“可能扩展”机械拆分。
- 业务能力、数据所有权和变化方向一致的代码保持内聚；只因复用几行工具代码不能合并领域边界。
- 只有独立扩缩容、发布、故障隔离、安全/合规、数据所有权或团队自治需求成立，并能承担分布式成本时才拆服务。
- 拆分后必须能够独立构建、测试、部署、回滚和观测；需要锁步发布的“微服务”视为分布式单体并应重新评估。
- 浏览器/移动界面进入 `apps/webs|mobiles`，无界面运行单元进入 `apps/servers`，独立工具进入 `apps/tools`，稳定跨应用代码能力才进入 `packages`。

## 依赖与模块

- 依赖指向更稳定的业务抽象；领域核心不得依赖框架、存储、网络、UI 或第三方 SDK。
- 模块通过公开用例、端口、契约或版本化事件协作，禁止跨模块深层导入、共享可变全局状态和绕过用例写数据。
- 同步调用用于调用方立即需要结果的核心流程；异步事件用于可延迟、可重试和无需生产者了解消费者的事实通知。
- 避免循环依赖。发现循环时优先重划业务所有权、提取稳定契约或反转依赖，不用 Service Locator 和全局事件总线掩盖。
- 共享包只承载稳定、无具体业务流程且已有多个真实消费者的能力；不能把服务间耦合包装成共享库。

## 数据与契约

- 每类业务数据只有一个写入所有者；其他模块/服务通过 API、事件或只读投影访问，不共享表写权限。
- 跨边界通信使用版本化契约，并明确认证、超时、重试、幂等、顺序和一致性语义。
- 数据库事务不能跨越多个独立服务；跨服务流程使用显式状态机、Outbox、Saga/补偿和对账。
- 新服务必须定义 SLO、容量假设、依赖、探针、故障模式、降级和数据恢复，而不只是新建目录和 Dockerfile。

## 演进与验证

- 优先兼容式渐进演进：先扩展生产者/消费者兼容范围，再迁移流量和数据，最后删除旧能力。
- 用真实瓶颈和运行证据驱动缓存、队列、读写分离、分库分表、微服务或多语言引入。
- 架构验证至少包含依赖方向检查、契约测试、消费者构建、失败注入和标准初始化；关键决策记录未验证假设。
- 设计完成不等于功能完成；必须有最小可运行路径、验证证据和可恢复交接。

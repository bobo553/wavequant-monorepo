# 后端可靠性与运行规范

本文件仅在任务涉及并发、异步任务、消息、Outbox、限流或背压时加载，并继承 `docs/agent/backend/rules.md`。探针、可观测、容器、发布和 IaC 改读 `docs/agent/operations/rules.md`。

## 请求生命周期与超时

- 入站请求统一经过请求标识/追踪、恢复、结构化访问日志、认证、授权、限流、校验和业务处理；中间件顺序必须可审阅和测试。
- Node HTTP Server、反向代理和 NestJS 入口协调配置 `headersTimeout`、`requestTimeout`、`keepAliveTimeout` 与优雅停机边界；请求体大小和连接池也必须有限制。
- 下游数据库、Redis、HTTP、队列和文件操作继承调用方取消信号，并设置比上游剩余预算更短的超时；禁止用 `context.Background()` 逃逸请求生命周期。
- 请求结束后仍需可靠完成的工作先持久化为任务或 Outbox，再由 Worker 执行；不得依赖未被等待和观测的临时 Promise。
- 超时代表结果未知时不能盲目重试副作用操作；通过幂等键或状态查询确认最终结果。

## 并发与背压

- 并发数量必须有上限，依据 CPU、内存、数据库连接、外部配额和下游吞吐设定；禁止按输入数量无限创建 Promise 或队列项。
- 独立 I/O 使用信号量、并发限制器或有界 Worker Pool，传播取消并明确 `fail-fast`、部分成功或聚合错误语义；不要对无界集合直接 `Promise.all`。
- Node.js 单线程并不等于没有竞态；共享缓存、数据库读改写、任务状态和重复事件仍需唯一约束、原子更新或版本控制。
- CPU 密集、压缩、图片处理和大批计算不得阻塞事件循环；按容量证据进入 Worker Thread、独立进程或任务队列。
- 内部生产速度超过消费能力时选择阻塞、有界排队、采样、丢弃或扩容，并明确数据是否允许丢失；禁止无界内存缓冲。
- 批量任务限制批次大小、并发、内存和执行时间，并支持取消、检查点与从断点恢复。

## 重试、熔断与隔离

- 重试只处理明确的瞬时错误，采用指数退避、随机抖动、最大次数和总时间预算；重试不得超过上游 Deadline。
- 非幂等操作只有具备业务幂等键或 Provider 幂等协议时才能自动重试；参数错误、认证失败和永久业务拒绝不重试。
- 熔断器用于阻止持续请求已失败的依赖，半开探测必须有限；降级响应必须真实表达能力受限，禁止伪造成功数据。
- 使用独立连接池、并发额度和队列隔离关键/非关键依赖，防止一个慢 Provider 耗尽全服务资源。
- 所有超时、重试、熔断和限流阈值进入强类型配置并有默认依据，不能散落魔法数字。

## 异步任务与消息

- 只有耗时、可延迟或非核心工作才异步化；核心事务必须在返回成功前完成，不能用队列隐藏尚未确认的业务结果。
- 异步受理返回 `202`、稳定任务 ID 和查询/通知方式；任务状态至少区分 queued、running、succeeded、failed/cancelled。
- 默认按至少一次投递设计：每条消息有全局事件 ID、事件类型、Schema 版本、发生时间、关联/因果标识和业务聚合 ID。
- 生产者等待 Broker 确认；Broker/队列按业务可靠性持久化；消费者完成数据库事务后再 ACK。
- 消费者以事件 ID、业务唯一键或状态机实现幂等。去重记录与业务写入必须处于同一事务或具备等效原子性。
- 重试按错误类型分类并退避；超过上限或无法解析的毒消息进入死信队列，保留失败原因、Payload 摘要和人工重放入口。
- 需要同一实体有序时按聚合 ID 分区并在消费者检查版本；禁止假设全局顺序，也不能让旧事件覆盖新状态。
- 消息 Schema 只做兼容演进；消费者先兼容新旧版本，再发布生产者。消息中不得携带不必要的敏感数据。

## Outbox 与跨服务一致性

- 业务状态和 Outbox 事件在同一数据库事务提交；发布器使用可抢占/可恢复的批次读取，成功发布后幂等标记。
- Outbox 记录包含唯一事件 ID、聚合 ID、类型、版本、Payload、创建时间、尝试次数和下次重试时间。
- 多个发布器并行时使用跳过锁定、租约或等效机制避免重复抢占；即使仍重复发布，消费者也必须幂等。
- 定义 Outbox 积压量、最老事件年龄、发布失败率和死信告警；定期归档/清理已发布记录且保留审计需求。
- 跨服务流程使用 Saga/补偿或显式状态机表达，不尝试把多个服务数据库包进单机事务。

## 限流、配额与负载保护

- 在边缘/网关保护总流量，在应用层按用户、设备、IP、租户、路由或业务资源保护细粒度配额；限流维度不能只依赖可伪造 Header。
- 令牌桶适合允许小幅突发，滑动窗口适合精确配额，漏桶适合平滑下游；选型依据业务语义和测量，不机械统一算法。
- 被限流返回 `429` 和合理的 `Retry-After`/配额信息；服务自身过载或依赖不可用使用 `503`，不要返回模糊 `500`。
- 登录、验证码、计费操作、Webhook、权益操作、搜索和大查询使用不同限额；成功与失败请求可采用不同策略以抵御滥用。
- 当队列积压或数据库连接接近上限时主动拒绝低优先级工作，保证已接收任务可完成；扩容不能替代有界背压。

## 可靠性验证清单

- 注入取消、超时、下游慢、连接池耗尽、重复投递、乱序和进程重启，验证系统不会泄漏任务或重复副作用。
- 对关键服务执行并发/竞态场景测试、容量基线和背压测试，记录吞吐、P95/P99、错误率、event-loop delay 与饱和点。
- 验证 Worker Drain、Outbox 积压恢复、死信重放、消费者重启和幂等记录清理。
- 涉及运行环境时同时按 `docs/agent/operations/rules.md` 验证探针、SIGTERM、日志、指标和 Trace。

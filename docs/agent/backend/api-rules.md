# 后端 API 与契约规范

本文件仅在任务涉及 HTTP、OpenAPI、DTO、错误、分页、版本或序列化时加载，并继承 `docs/agent/backend/rules.md`。

## 契约优先

- 跨 Web、Mobile、API 的公开数据结构以 `@repo/contracts` 中的 Zod Schema 和推导类型为事实来源；NestJS DTO、Swagger Metadata 与实现必须保持一致。
- 实现端点前先定义路径、方法、认证、请求、响应、错误、幂等、分页和限流语义，再实现服务端与消费者。
- OpenAPI 必须描述所有成功和可预期错误响应、认证方案、必填 Header、示例与字段约束；实现、文档和测试不得各自漂移。
- 契约变更要检查所有生产者与消费者。破坏性变更使用新版本或兼容迁移，不得静默改变字段类型、枚举语义或默认值。
- 契约影响面至少核对请求/响应/错误类型、路由或 RPC 声明、Handler、application 用例与端口、外部调用方、消息生产/消费端、配置、文档、生成物、测试、部署顺序和灰度兼容；不能只改服务端单点。
- 生成客户端、OpenAPI 产物或胶水代码必须从权威 Schema 用仓库固定版本重复生成；识别生成标记，禁止手工修改，并审阅生成前后 Diff 是否包含意外行为变化。
- 未使用 gRPC 或代码生成时不得为未来假设提前引入；真正引入时需明确权威 Schema、版本兼容、生成命令和消费者验证。

## HTTP 资源与方法

- URL 表示资源，统一使用小写、复数名词和 kebab-case；过滤、排序、分页与可分享查询使用 Query，避免动词路径和过深嵌套。
- `GET/HEAD` 只读且可安全重试；`PUT/DELETE` 保持幂等；`POST/PATCH` 的重试语义必须明确。
- 创建资源、提交任务、调用计费或发放权益等重复执行会产生副作用的操作必须支持幂等键或业务唯一键，并校验同一键对应的请求摘要一致。
- 成功创建返回 `201` 并在适用时提供资源位置；无响应体使用 `204`；异步受理返回 `202`、任务 ID 和状态查询入口。
- 使用标准状态码表达结果：输入不合法 `400/422`、未认证 `401`、无权限 `403`、不存在 `404`、冲突 `409`、限流 `429`、暂不可用 `503`。禁止所有结果都返回 `200`。
- `DELETE` 的重复调用语义、批量接口的部分成功策略以及 `PATCH` 的字段清除语义必须在契约和测试中明确。

## 输入边界

- 路径、Query、Header、Cookie 和 Body 均视为不可信输入；在 presentation 边界完成类型、范围、长度、格式、枚举和业务标识校验。
- 限制请求头、Body、JSON 深度、集合长度、字符串长度和上传体积；流式读取大请求，禁止无上限一次性载入内存。
- 明确支持的 `Content-Type` 和字符集，不匹配时拒绝；JSON 默认使用 UTF-8。
- 对未知字段采用明确策略：公开写接口通常拒绝拼写错误的字段；为兼容而忽略时必须有契约测试，不能无意吞掉输入。
- 客户端传入的用户 ID、租户/资源所有者、角色、金额、价格、权益和状态不能作为权威值；从登录态、服务端数据或配置重新解析。
- CORS 使用精确来源、方法和 Header 白名单；不得在携带凭据时允许通配来源。

## 响应与错误

- API 返回专用 Response DTO，只暴露客户端需要且允许访问的字段；不得返回 ORM 实体、内部状态、数据库列名或第三方原始响应。
- 同一 API 族使用稳定错误结构，至少包含机器可读 `code`、安全的 `message` 和 `requestId`；字段错误可附带受控 `details`。
- 错误码代表稳定业务语义，不绑定中文文案、类名或数据库错误；客户端不得靠解析 `message` 做流程判断。
- `message` 面向调用方说明可采取的行动，但不得泄露堆栈、SQL、内部路径、凭据、签名材料或用户隐私。
- 只在边界记录一次完整错误链，并附请求/追踪标识；客户端错误不按服务故障记录，服务端故障必须进入指标与告警。
- 列表响应的分页元数据、空列表、资源不存在和字段缺省语义保持一致；禁止同一字段在对象、数组和 `null` 之间随意变化。

## 分页、查询与并发控制

- 小而稳定的数据集可用 offset 分页；大数据或实时变化列表优先使用稳定排序字段加唯一 ID 的 cursor 分页。
- 排序字段、过滤字段和最大页大小使用白名单；禁止把客户端字符串直接拼接为 SQL、ORM 字段或搜索表达式。
- Cursor 必须不透明、可校验并绑定排序语义；客户端不能依赖其内部编码。
- 支持并发编辑的资源使用版本号、ETag/`If-Match` 或领域版本做乐观并发控制；冲突返回 `409` 或 `412`，不能静默覆盖。
- 批量 API 设置数量与总负载上限，并明确原子成功、逐项结果或异步任务三者之一。

## 序列化约定

- 公共 HTTP 默认 JSON；只有性能、流量或跨语言 RPC 的测量证据足够时才引入 Protobuf/MessagePack，且必须保留版本化 Schema。
- 时间统一传输 RFC 3339/ISO 8601 且包含时区，服务端内部优先 UTC；仅日期使用 `YYYY-MM-DD`，不要伪装成零点时间。
- 金额使用最小货币单位整数或明确精度的十进制字符串，并同时携带币种；禁止使用二进制浮点表示订单、支付和账本金额。
- 可能超过 JavaScript 安全整数范围的 ID/计数以字符串传输；布尔值、数字和枚举不得用含糊字符串代替。
- 明确 `null`、字段缺省和空集合的差异；新增可选字段应向后兼容，重命名或复用既有字段前必须升级契约。
- 对外枚举按开放世界处理：服务端不复用旧值表达新含义，客户端应能安全处理未知新值。
- 缓存、消息和存档 Payload 包含 Schema/事件版本；反序列化失败进入可观测错误路径，不能用零值继续执行业务。

## 版本与缓存

- 优先通过兼容新增字段演进；确需破坏性变更时使用明确版本边界，并记录迁移、废弃和下线条件。
- 版本下线必须基于调用量和消费者迁移证据；旧客户端仍在使用时不得直接删除端点。
- 可缓存响应显式设置 `Cache-Control`、ETag 或 `Last-Modified`；用户私有、支付和权限数据默认 `no-store` 或私有缓存。
- 缓存键必须包含会影响响应的身份、租户/资源范围、语言和版本维度，避免跨用户或跨租户数据泄漏。
- 反向代理压缩和缓存只用于适合的内容类型与体积；不得对已压缩文件重复压缩或缓存带敏感凭据的响应。

## 外部 API 客户端

- 每个外部服务使用集中 Client/Adapter，统一 base URL、认证、连接池、超时、响应体上限、错误映射和遥测。
- 重试仅用于瞬时错误和可安全重放的操作，采用指数退避与随机抖动并设置次数/总时长预算；尊重服务端 `Retry-After`。
- 非幂等请求没有幂等协议时不得自动重试；超时结果未知的支付/创建操作先查询状态，不能盲目再次提交。
- TLS 证书验证不得关闭；重定向、代理和目标地址使用白名单，防止凭据转发与 SSRF。
- 第三方响应先校验状态、Content-Type、Schema 和大小，再映射为内部模型；不得把 Provider 错误原样传给客户端。

## API 验证清单

- 契约校验：OpenAPI/Schema 可解析，生成物可重复，消费者类型检查通过。
- 行为测试：成功、校验失败、未认证、无权限、不存在、冲突、限流和依赖失败。
- 边界测试：最大负载、未知字段、非法编码、超大页、重复幂等键和并发版本冲突。
- 兼容测试：旧请求仍可用，新字段缺省安全，序列化跨语言不丢精度和时区。
